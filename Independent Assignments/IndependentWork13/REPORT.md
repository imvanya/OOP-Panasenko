# Звіт: кейси Polly/Retry

**Проєкт:** `IndependentWork13` (.NET 8, пакет `Polly.Core` 8.x, API `ResiliencePipelineBuilder`). Запуск: `dotnet run`.

У роботі реалізовано три сценарії, відмінні від прикладу з методички (там розглянуто виклик зовнішнього API з Retry):

| № | Сценарій | Політики Polly | Файл |
|---|---|---|---|
| 1 | Тимчасові збої підключення до БД | Retry (експоненційна затримка, вибіркова обробка винятків) | `DatabaseScenario.cs` |
| 2 | Перевантажена черга повідомлень | Circuit Breaker + Fallback | `QueueScenario.cs` |
| 3 | Занадто довга операція (генерація звіту) | Retry + Timeout | `ReportScenario.cs` |

Логування виконується через `Console.WriteLine` (клас `Logger`) із часовою позначкою `[HH:mm:ss.fff]`. Збої імітуються лічильниками викликів, а затримки: `Thread.Sleep` (сценарії 1–2) і `Task.Delay` (сценарій 3). Нижче наведено **реальний вивід програми**, отриманий під час запуску.

## Сценарій 1. Доступ до бази даних (Retry)

### Проблема
Підключення до БД може тимчасово обриватися: перезапуск сервера, пікове навантаження, мережевий збій. Такі помилки **минущі**: повторний запит через мить, найімовірніше, спрацює. Водночас деякі помилки (порушення унікальності, синтаксична помилка) **постійні**, і повторення лише марнує час та навантажує БД.

### Вибір політики
**Retry** із такими налаштуваннями:
- `ShouldHandle` обробляє лише `TransientDbException`. Постійна помилка (`PermanentDbException`) не повторюється й одразу потрапляє до викликаючого коду.
- `BackoffType = Exponential`, `Delay = 300 мс`: затримки 300 → 600 → 1200 мс. Зростаюча пауза дає БД час відновитися й не навантажує її частими запитами.
- `MaxRetryAttempts = 3`: обмеження кількості повторів.
- `UseJitter = false` для відтворюваного виводу. У реальному застосунку краще `true`, щоб клієнти не повторювали запити синхронно.

### Код
```csharp
var pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<TransientDbException>(),
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromMilliseconds(300),
        BackoffType = DelayBackoffType.Exponential,
        UseJitter = false,
        OnRetry = args =>
        {
            Logger.Log($"Retry #{args.AttemptNumber + 1} через {args.RetryDelay.TotalMilliseconds:F0} мс. " +
                       $"Причина: {args.Outcome.Exception?.Message}");
            return default;
        }
    })
    .Build();

string result = pipeline.Execute(() => database.Query("SELECT * FROM Orders"));
```

Затримки збільшуються вдвічі, як і передбачає експоненційна стратегія. Третя спроба успішна, і викликаючий код отримує результат так, ніби збоїв не було.
- **Запуск 2.** Постійна помилка виконується **один раз**: немає рядків `Retry`, виняток одразу доходить до `catch`. Це результат вибіркового `ShouldHandle`: повторювати порушення унікальності безглуздо.

## Сценарій 2. Перевантажена черга повідомлень (Circuit Breaker + Fallback)

### Проблема
Брокер повідомлень (RabbitMQ, Kafka тощо) перевантажений і відхиляє запити. Якщо продовжувати слати кожне повідомлення й чекати на відповідь, застосунок витрачає ресурси на заздалегідь невдалі виклики, а брокер, який і так «задихається», отримує ще більше навантаження. Крім того, повідомлення не можна просто втрачати.

### Вибір політики
Комбінація двох стратегій (перша додана є зовнішньою):
1. **Fallback** (зовнішній): якщо відправка не вдалась або виклик заблоковано, повідомлення зберігається в локальний буфер (outbox) для повторної відправки пізніше. Так дані не втрачаються.
2. **Circuit Breaker** (внутрішній): після серії збоїв «розмикає ланцюг» і певний час відхиляє виклики миттєво (`BrokenCircuitException`), не звертаючись до брокера. Це дає брокеру час відновитися й економить ресурси клієнта. Після паузи пропускається один пробний виклик (half-open): успішний закриває ланцюг, невдалий знову розмикає.

Налаштування: `MinimumThroughput = 3`, `FailureRatio = 0.5`, `SamplingDuration = 10 с`, `BreakDuration = 2,1 с`. Retry тут навмисно не використано: повторні запити лише погіршили б перевантаження.

### Код
```csharp
var pipeline = new ResiliencePipelineBuilder<string>()
    .AddFallback(new FallbackStrategyOptions<string>
    {
        ShouldHandle = new PredicateBuilder<string>()
            .Handle<BrokerOverloadedException>()
            .Handle<BrokenCircuitException>(),
        FallbackAction = _ => new ValueTask<Outcome<string>>(Outcome.FromResult("BUFFERED")),
        OnFallback = args => { Logger.Log($"Fallback: ... ({args.Outcome.Exception?.GetType().Name})"); return default; }
    })
    .AddCircuitBreaker(new CircuitBreakerStrategyOptions<string>
    {
        ShouldHandle = new PredicateBuilder<string>().Handle<BrokerOverloadedException>(),
        FailureRatio = 0.5,
        SamplingDuration = TimeSpan.FromSeconds(10),
        MinimumThroughput = 3,
        BreakDuration = TimeSpan.FromMilliseconds(2100),
        OnOpened = args => { Logger.Log($"Circuit OPEN: ... {args.BreakDuration.TotalSeconds:F1} с"); return default; },
        OnHalfOpened = args => { Logger.Log("Circuit HALF-OPEN: пробний виклик"); return default; },
        OnClosed = args => { Logger.Log("Circuit CLOSED: брокер відновився"); return default; }
    })
    .Build();
```
Брокер імітується так, що перші 3 виклики завершуються `BrokerOverloadedException`, а далі працює нормально. Відправляється 10 повідомлень з інтервалом 600 мс.

## Сценарій 3. Довга операція (Retry + Timeout)

### Проблема
Генерація звіту інколи «зависає»: запит до сховища чи зовнішнього сервісу не відповідає або виконується занадто довго. Без обмеження часу потік (або користувач) очікує нескінченно, ресурси блокуються.

### Вибір політики
Комбінація **Timeout** (внутрішній) і **Retry** (зовнішній):
- **Timeout = 1 с** обмежує час **кожної спроби**: Polly скасовує `CancellationToken` і викидає `TimeoutRejectedException`.
- **Retry** повторює операцію лише при `TimeoutRejectedException` (до 3 разів, з постійною паузою 500 мс): зависання зазвичай разове, наступна спроба може бути швидкою.
- Порядок важливий: Timeout додано **після** Retry, тобто він вкладений у нього, тому відлік 1 с починається заново для кожної спроби. Якби Timeout був зовнішнім, він обмежував би загальний час усіх спроб.

Важливий нюанс: Timeout у Polly **кооперативний**. Він лише сигналізує через `CancellationToken`, а операція має сама на нього реагувати. Тому в цьому сценарії замість `Thread.Sleep` (який не можна перервати) використано `await Task.Delay(ms, token)` та виклик через `ExecuteAsync`.

### Код
```csharp
var pipeline = new ResiliencePipelineBuilder()
    .AddRetry(new RetryStrategyOptions
    {
        ShouldHandle = new PredicateBuilder().Handle<TimeoutRejectedException>(),
        MaxRetryAttempts = 3,
        Delay = TimeSpan.FromMilliseconds(500),
        BackoffType = DelayBackoffType.Constant,
        UseJitter = false,
        OnRetry = args => { Logger.Log($"Retry #{args.AttemptNumber + 1} ..."); return default; }
    })
    .AddTimeout(new TimeoutStrategyOptions
    {
        Timeout = TimeSpan.FromSeconds(1),
        OnTimeout = args => { Logger.Log($"Timeout: ... {args.Timeout.TotalSeconds:F1} с"); return default; }
    })
    .Build();

string file = await pipeline.ExecuteAsync<string>(async token => await GenerateReportAsync(token));
```
Перші дві спроби «зависають» на 3 с, третя виконується за 300 мс.

- Між `Timeout` і наступною спробою проходить пауза 500 мс (48.604 → 49.104), заданий у Retry.
- Третя спроба виконується за 300 мс, у межах ліміту, і повертає результат.
- Загальний час: 47.575 → 50.907 ≈ 3,3 с. Без тайм-ауту лише перша «зависла» спроба тривала б 3 с, а повторних спроб не було б.

## Загальні висновки

**Переваги Polly**
- **Декларативність.** Політики описуються в одному місці (`ResiliencePipelineBuilder`), а бізнес-код не засмічений циклами повторів і вкладеними `try/catch`.
- **Готові перевірені стратегії.** Retry, Circuit Breaker, Timeout, Fallback, Hedging, Rate Limiter: не потрібно писати власну (часто помилкову) логіку затримок, станів і потокобезпечності.
- **Композиція.** Стратегії легко поєднуються в пайплайн (Retry + Timeout, Fallback + Circuit Breaker), а порядок визначає поведінку. Це добре видно у сценаріях 2 та 3.
- **Вибірковість і спостережуваність.** `ShouldHandle` дозволяє повторювати лише тимчасові помилки (сценарій 1), а події `OnRetry`, `OnOpened`, `OnTimeout` та інші дають змогу бачити реакцію політик у логах.
- **Захист залежностей.** Circuit Breaker (сценарій 2) припиняє навантажувати нестабільний сервіс і дозволяє швидко «деградувати» через Fallback замість тривалого очікування.

**Обмеження та ризики**
- **Ідемпотентність.** Повторювати можна лише операції, які безпечно виконати двічі. Retry на оплаті чи створенні замовлення без ідемпотентності може призвести до дублювання.
- **Шторм повторів.** Без затримки, jitter і обмеження спроб клієнти можуть перевантажити вже слабкий сервіс. Circuit Breaker частково це компенсує.
- **Кооперативний Timeout.** Без підтримки `CancellationToken` в самій операції вона продовжить працювати після спрацювання тайм-ауту.
- **Підбір параметрів.** Кількість спроб, затримки й пороги залежать від конкретної системи й потребують налаштування та моніторингу.
- **Не усуває причину.** Polly маскує тимчасові проблеми, але постійні помилки все одно треба діагностувати та виправляти.
- **Fallback потребує узгодженості.** Локальний буфер зі сценарію 2 треба згодом доправити в чергу, вирішивши питання порядку та дублікатів.

**Підсумок.** Polly дозволяє суттєво підвищити відмовостійкість застосунку невеликою кількістю коду, якщо обирати політику відповідно до типу збою: Retry для тимчасових, Circuit Breaker для тривалої недоступності залежності, Timeout проти зависань, Fallback для коректної деградації. Результати запусків підтверджують очікувану поведінку всіх трьох сценаріїв.
